# Telecom Data Platform

A small streaming data platform that simulates telecom events, publishes them into Kafka, stores the raw data in a bronze layer, and validates/cleans the data in a Spark silver layer.

The project is designed to demonstrate a practical event-driven pipeline for customer, billing, and network telemetry without requiring a full enterprise stack.

## Architecture

The pipeline follows this flow:

Producer -> Kafka topics -> Spark Structured Streaming (Bronze) -> Silver processing -> Parquet datasets

At a high level:

- Synthetic telecom events are generated by Python producer scripts.
- Events are published to Kafka topics such as `customer-events`, `billing-events`, and `network-events`.
- Spark reads each Kafka stream and writes the raw payloads to Parquet in `data/bronze/...`.
- A reusable silver processor reads the bronze Parquet datasets, filters invalid records, normalizes `event_type`, and writes cleaned datasets to `data/silver/...`.
- Consumer scripts also capture raw JSONL payloads into `data/*.jsonl` for a simple operational replay/debugging view.

## Included event domains

This project processes three telecom event families:

- Customer events: signups, churn, support interactions, package changes
- Billing events: invoices, payments, refunds, late payment events
- Network events: calls, data sessions, outages, roaming, speed tests

## Prerequisites

Before running the project, install:

- Docker and Docker Compose
- Python 3.9+
- `pip` package manager

Install the Python dependencies:

```bash
python -m venv .venv
source .venv/bin/activate
pip install kafka-python Faker pyspark
```

## Start the platform services

From the project root, start Kafka and the Spark cluster:

```bash
docker compose up -d
```

This starts:

- Kafka broker on `localhost:9092`
- Spark master on `localhost:8080`
- Spark worker on `localhost:8081`

You can verify container health with:

```bash
docker ps
```

## Run the producers

Each producer generates a continuous stream of synthetic telecom events and pushes them to Kafka.

Open separate terminals and run:

```bash
python producer/customer_events.py
```

```bash
python producer/billing_events.py
```

```bash
python producer/network_events.py
```

Each script emits events every few seconds, creating realistic JSON payloads such as customer activity, billing events, and network usage metrics.

## Run the Kafka consumers

The consumer scripts read the topic streams and append the raw messages to JSONL files in `data/`.

```bash
python consumer/customer_events_consumer.py
python consumer/billing_events_consumer.py
python consumer/network_events_consumer.py
```

This produces:

- `data/customer_events.jsonl`
- `data/billing_events.jsonl`
- `data/network_events.jsonl`

## Run the bronze ingestion layer

The bronze Spark scripts subscribe to Kafka topics and store the JSON payloads as Parquet to the bronze landing area.

Start each stream in a separate terminal:

```bash
python spark/bronze/bronze_customer_events.py
```

```bash
python spark/bronze/bronze_billing_events.py
```

```bash
python spark/bronze/bronze_network_events.py
```

These scripts create parquet partitions under:

- `data/bronze/customer_events`
- `data/bronze/billing_events`
- `data/bronze/network_events`

Each bronze job also writes checkpoint metadata to the matching folder in `checkpoints/` so the streaming job can recover state across restarts.

## Run the silver processing layer

The silver layer is driven by the shared processor in `spark/silver/silver_event_processor.py`.

The common transformation logic:

- reads the bronze parquet data
- removes rows where required fields are null
- ensures `event_type` is lowercased
- adds a `processed_timestamp`
- writes the cleaned result to `data/silver/<event_name>`

Run the silver jobs:

```bash
python spark/silver/silver_customer_events.py
```

```bash
python spark/silver/silver_billing_events.py
```

```bash
python spark/silver/silver_network_events.py
```

These create outputs such as:

- `data/silver/customer_events`
- `data/silver/billing_events`
- `data/silver/network_events`

## Silver processor behavior

The shared helper is intentionally lightweight and reusable:

```python
from silver_event_processor import process_silver_events

if __name__ == "__main__":
    process_silver_events("customer_events")
```

The default validation keeps rows with non-null `event_id` and `customer_id`, which makes it easy to extend the pipeline for additional domains by creating a new entrypoint script using the same helper.

## Example data model

Each event contains a shared telemetry envelope plus domain-specific fields. For example:

- `event_id`
- `customer_id`
- `event_type`
- `event_timestamp`
- domain-specific attributes like `package_name`, `bill_amount`, or `network_type`

This schema pattern keeps the pipeline flexible while preserving a consistent event model across all event categories.

## Notes

- All Spark jobs use relative paths from the project root, so run them from the repository root directory.
- Kafka and Spark services must be running before the producer and bronze jobs are started.
- If you want to restart the pipeline cleanly, remove the generated data and checkpoint folders before rerunning the jobs.

## Typical end-to-end flow

```bash
# 1. Start infrastructure
docker compose up -d

# 2. Activate your Python environment
source .venv/bin/activate

# 3. Start data generation in separate terminals
python producer/customer_events.py
python producer/billing_events.py
python producer/network_events.py

# 4. Consume raw messages (optional)
python consumer/customer_events_consumer.py
python consumer/billing_events_consumer.py
python consumer/network_events_consumer.py

# 5. Land raw data in bronze
python spark/bronze/bronze_customer_events.py
python spark/bronze/bronze_billing_events.py
python spark/bronze/bronze_network_events.py

# 6. Clean and standardize in silver
python spark/silver/silver_customer_events.py
python spark/silver/silver_billing_events.py
python spark/silver/silver_network_events.py
```

This repo is a compact reference implementation of a streaming telecom analytics pipeline using Kafka and Spark, ideal for learning how event-driven data ingestion and bronze/silver processing work together in practice.
